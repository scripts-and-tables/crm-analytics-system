Everything on this site is fictional.

The company does not exist. Every client, order, amount, staff member and log entry is machine-generated, and contact details use the reserved .example domains so no generated record can address a real mailbox. The demo says so on every screen.

FAQ

The questions people actually ask

Is any of this real customer data?

No, and it never was. A seeded Python script invents the customers, the products and five years of invoices. Names come from a fictional name pool, and email addresses use the .example domains reserved by RFC 2606 precisely so documentation cannot reach a real inbox.

Why do the portal and the dashboard segment clients differently?

Because they are two different artifacts, and the site does not pretend otherwise. The dashboard charts the RFMT model in the business-logic spec — Diamond through Bronze, driven by consumable volume and order frequency. The portal is a product prototype for a different fictional business, and tiers clients by trailing-12-month spend instead.

Merging them onto one model is the obvious next step; presenting them as if they already share one would be the dishonest shortcut.

Can I run it myself?

Yes — clone the repo, install the requirements, and run the generator, the build and the report script in that order. The README lists the commands. It needs no server, no API key and no account.

Why RFMT and not plain RFM?

Recency, frequency and monetary value decide the tier; tenure is carried alongside as tenure_months so cohorts can be compared without letting length of relationship inflate a tier on its own.

Why exclude devices from the engagement metrics?

Because a device is bought once. Counting it would make a single-purchase buyer look loyal. Only recurring consumable lines drive the value tier; the one device-based field kept is the date of the first device purchase.
